# LINE 長輩圖智慧自動回覆機器人 (line-grandma-bot)

[![Version](https://img.shields.io/badge/version-2.15.0-blue.svg)](auto_reply.py)
[![Platform](https://img.shields.io/badge/platform-Windows%2010%20%7C%2011-0078D6.svg)](https://microsoft.com)
[![Python](https://img.shields.io/badge/python-3.10%2B-green.svg)](https://python.org)
[![License](https://img.shields.io/badge/license-MIT-lightgrey.svg)](LICENSE)

專為 Windows LINE 個人電腦版設計的**長輩圖智慧自動回覆守護程式**。  
當長輩或親友傳來長輩圖時，程式會以真人般隨機延遲時間，自動回傳一張**不重複、高畫質的正統台灣長輩圖**；對方傳**短問候文字**（例如「早安」「中秋節快樂」）時也回同性質的圖，其餘文字訊息保持沈默，**維持對話未讀狀態不秒讀**。

---

## 🌟 核心特色

### 1. 獨立「百輪雙向記憶庫」
* 為每位監控好友維護各自獨立的雙向歷史紀錄（預設 100 輪）。
* **保證 100 輪內絕不重複發送同一張圖**給該對象。
* **絕不回送對方曾傳來過的圖片**給對方（防失禮尷尬機制）。

### 2. 跨好友「借花獻佛」大循環
* 好友 A 傳來的正統長輩圖，在 A 的百輪記憶中被封印（不回發給 A）。
* 系統會自動將該圖收納進中央圖庫，日後「借花獻佛」流通發送給好友 B 或好友 C。

### 3. Windows 原生 OCR 真偽鑑別（非長輩圖不收）
* 整合 Windows 10/11 內建繁體中文 OCR 引擎（`Windows.Media.Ocr`）。
* 自動辨識並核對「早安、平安、喜樂、祝福、健康、美好」等核心問候關鍵字。
* 若對方傳送的是生活隨拍照、寵物照、發票或收據，自動拒絕入庫，確保圖庫血統純正。

### 4. 台塑貼圖酷官方圖庫爬蟲（杜絕雜圖）
* 連線台灣 Formosa「台塑貼圖酷」官方長輩圖專案，精準收錄上千幅高解析度每日問候與插畫。
* 具備連線熔斷保護、MD5 指紋去重、單檔 8MB 記憶體上限防護。
* 支援 7 天 TTL 自動過期清理與發送後自動補新圖機制。

### 5. 高 DPI 縮放校正與穩定性防護
* 啟用 Windows 原生 Per-Monitor V2 DPI 感知（`SetProcessDpiAwareness`），徹底解決筆電 125%/150% 螢幕縮放時的滑鼠座標漂移問題。
* 全面採用 `tempfile` + `os.replace` 原子寫入（Atomic Write），杜絕斷電或當機導致 JSON 資料檔損毀。
* 全域例外捕獲與自動退避復原，滑鼠甩至角落觸發防護時守護程式永不閃退中斷。

### 6. 背景動態名單熱更新（Hot Reload）
* 守護程式在背景執行期間，手動修改 `config.json` 新增或移除好友名單，**秒級自動生效**，無需手動重啟程式。

## 🚀 快速開始

### 1. 系統需求
* 作業系統：Windows 10 / Windows 11 (64 位元)
* Python 版本：Python 3.10 或以上（建議 Python 3.12+）
* 電腦版 LINE：保持登入並正常運作

### 2. 標準操作流程 (SOP)
為確保自動化運作 100% 穩定且絕不干擾其他對話，建議採用以下極簡標準流程：
1. **開啟目標獨立聊天室**：在 LINE 電腦版的好友清單中，對 `config.json` 內設定的目標好友（例如「媽媽」）連點兩下開啟**獨立聊天室視窗**（直接最小化至工作列即可）。
2. **零設定全自動守護 (Zero-Config)**：直接啟動 `run_auto_reply.bat`。程式具備動態頻道自動學習技術，當目標好友傳來長輩圖或貼圖時，背景全自動完成頻道綁定與回覆，**完全無需任何手動校準指令**。
3. **安全回覆與自動最小化**：程式喚醒視窗、驗證視窗身分與訊息方向後貼圖送出，並自動重新最小化維持未讀狀態，完全不干擾您在 LINE 主視窗與其他親友交談。
> **初次綁定需保持視窗可見**：尚未綁定的頻道要靠聊天視窗的異動來比對，最小化的視窗讀不到指紋，程式為避免搶奪焦點也不會自動彈出視窗，日誌會顯示「視窗處於最小化狀態」。若視窗在 15 秒內仍未還原，該張圖會被略過、不補回覆。請先還原並保持視窗可見，等第一張圖綁定成功後即可最小化。

### 3. 安裝相依套件
在專案根目錄開啟 PowerShell，執行：
```powershell
pip install -r requirements.txt
pip install --ignore-requires-python rapidocr-onnxruntime
```
第二行安裝離線 OCR。它宣告只支援 Python 3.12 以下，Python 3.13 以上不加 `--ignore-requires-python` 會安裝失敗；沒裝時退回 Windows 內建 OCR，辨識率大幅下降。

### 4. 設定監控名單
首次使用時，請複製 `config.example.json` 為 `config.json`：
```powershell
copy config.example.json config.json
```
使用任何文字編輯器開啟 `config.json`，在 `targets` 陣列填入欲監控回覆的好友 LINE 顯示名稱：
```json
{
  "targets": [
    "媽媽",
    "爸爸",
    "大舅舅"
  ],
  "images_dir": "images",
  "trigger_mode": "photo_and_sticker",
  "min_delay_seconds": 5,
  "max_delay_seconds": 900,
  "cooldown_seconds": 30,
  "history_rounds": 100,
  "replace_after_send": true,
  "collect_incoming_images": true,
  "image_ttl_days": 7,
  "min_image_pool": 10,
  "auto_crawl_images": true,
  "close_window_after_send": true,
  "time_aware_images": true,
  "max_replies_per_day": 3,
  "max_image_pool": 120,
  "instant_crawl_max_downloads": 40,
  "stop_command": "結束長輩圖機器人",
  "stop_command_chats": [],
  "notify_log": false,
  "notify_monthly_cap": 150,
  "notify_fallback_chat": "Notify Bot"
}
```

#### ⚙️ 設定參數詳解
| 參數名稱 | 預設值 | 說明 |
| :--- | :---: | :--- |
| `targets` | `["媽媽"]` | 監控回覆的好友名稱陣列（支援多位好友，需與 LINE 上顯示名稱完全相符）。 |
| `images_dir` | `"images"` | 長輩圖存放資料夾路徑。 |
| `trigger_mode` | `"photo_and_sticker"` | 回覆觸發模式：`"photo_and_sticker"`（預設，對方發照片時回覆長輩圖；貼圖與文字不是靠快取偵測，另由「視窗列表監看」處理，見 `reply_to_sticker_text`、`reply_to_text`）；`"photo_only"`（僅限對方傳照片時回覆）；`"all"`（文字、貼圖與照片皆回覆）。 |
| `min_delay_seconds` | `5` | 模擬真人延遲回覆**最短秒數**。 |
| `max_delay_seconds` | `900` | 模擬真人延遲回覆**最長秒數**（預設 900 秒 = 15 分鐘，每次會在此區間內隨機擲出秒數）。等待期間監聽暫停（日誌每分鐘倒數），此時其他聊天室的新圖不會被處理，且未綁定頻道的自動綁定可能因時間差過大被拒；等待結束後仍會重新核驗視窗、前景與方向，並重驗時段。 |
| `cooldown_seconds` | `30` | 防洗版全域冷卻安全間隔（秒）。 |
| `history_rounds` | `100` | 每位好友獨立記憶輪數（100 輪內不發送相同圖片，也不把對方曾傳給你的圖片回傳）。 |
| `collect_incoming_images` | `true` | 是否透過原生 OCR 自動辨識並收納對方傳來的長輩圖進入圖庫（借花獻佛）。 |
| `replace_after_send` | `true` | 圖片送出後是否立即從本機淘汰，並自動從網路抓取全新長輩圖遞補。 |
| `image_ttl_days` | `7` | 網路抓取的長輩圖保存期限（天），過期自動清理換新以保持圖庫新鮮。 |
| `min_image_pool` | `10` | 圖庫最低儲備數量，低於此數量時自動連網補充。 |
| `auto_crawl_images` | `true` | 是否允許圖庫不足時自動連網下載補充。 |
| `close_window_after_send` | `true` | 發送完成後是否自動將對話框最小化至工作列，維持後續未讀狀態。 |
| `close_opened_windows` | `true` | **機器人自己從主視窗開出來的**聊天視窗，回覆完或自動綁定完直接**關閉**（不是最小化）。三種視窗一律不碰：你本來就開著的、文字偵測正在監看的（關掉就偵測不到下一則文字）、登記超過 1 小時的（可能已經是你在用）。設 `false` 就照 `close_window_after_send` 最小化。 |
| `stop_command` | `"結束長輩圖機器人"` | 停止指令的文字。你在 `stop_command_chats` 內的聊天室自己發了含此文字的訊息，程式立即結束。比對時忽略空白與標點，OCR 認錯一字也算（例如「結束長輩圖機器八」）。 |
| `stop_command_chats` | `[]` | 接受你下停止指令的聊天室名單，名稱需與 LINE 顯示名稱完全相符（例如官方帳號 `Notify Bot`）；空白代表停用此功能。只認「你自己發」的訊息，對方傳來的不算；聊天室需開成獨立視窗並保持展開（不能最小化）。 |
| `auto_neutral_images` | `false` | **已被新的挑圖規則取代，不影響回覆**，只剩舊的 `--fill-pool` / `--tag-image` 時段標記還會參考。 |
| `group_targets` | `[]` | 要回覆的**群組**名單，名稱寫法同 `targets`（不含人數，例如 `理財幼幼班_Z`）。群組有更保守的專屬規則（見下方），快取頻道只能手動綁定：`python auto_reply.py --bind-view "群組名稱"`，30 秒內在該群組的獨立視窗點開一張**真正的照片**（不能是貼圖）。 |
| `group_max_replies_per_day` | `1` | 每個群組每天最多回覆幾次（本機午夜重置；`0` = 不限次數）。 |
| `group_cooldown_seconds` | `600` | 同一個群組兩次回覆之間至少間隔幾秒，避免多人連續傳圖時一直回。 |
| `reply_to_text` | `true` | 對方傳來的**短文字訊息**（例如「早安」「中秋節快樂」）屬於本專案處理的性質（節日、平安叮嚀、祝福鼓勵、時段問候、心靈雞湯）時，也回同性質但不同張的圖。只限一對一聊天室，不需要綁定快取頻道；與圖片共用每日上限與冷卻。**該好友的視窗要「展開、放在背景」，不能縮小**（見 v2.12.0）。讀文字要把聊天視窗帶到前景，不想被打擾就設 `false`。 |
| `require_grandma_image` | `true` | 對方傳來的圖要先被辨識成「長輩圖」（OCR 讀得出節日、問候、祝福等性質）才回；生活照、辨識不出性質的圖、競選圖一律略過，**貼圖預設也略過**（見 `reply_to_sticker_text`）。設為 `false`（**只對一對一有效**）就不辨識：任何照片或貼圖都照現在時段回一張問候圖。**群組一律強制辨識，設成 `false` 也一樣。** |
| `reply_to_sticker_text` | `true` | 一對一：貼圖上**寫著短問候或祝福**（例如「早安安」）時，OCR 讀出來也回同性質但不同張的圖；生日祝賀只回「謝謝」。其他貼圖（沒有字、寫「OK啦」「哈哈哈」之類）照舊略過。字數上限與文字訊息共用 `text_reply_max_chars`，競選字不算、生日要有祝賀語才算。**群組不適用**（群組的貼圖一律略過）。**該好友的視窗要「展開、放在背景」，不能縮小**（貼圖不會寫進聊天室的快取，和文字訊息一樣靠視窗列表監看偵測，見 v2.12.0、v2.14.0）；停止指令聊天室（如 Notify Bot）不適用。**設定檔沒寫這一項時，跟著 `reply_to_text`**（原本為了「不想被打擾」關掉文字回覆的人，貼圖也不會把視窗帶到前景）；明確寫 `true` 或 `false` 就照寫的。`trigger_mode` 為 `photo_only`（只回照片）時貼圖不處理。設為 `false` 貼圖一律略過。詳見下方「一對一與群組的差異」。 |
| `birthday_reply` | `"謝謝"` | 一對一收到「生日快樂」的**圖或短文字**時，只回這句話（打進輸入框送出），不回圖；算一次回覆，與其他回覆共用每日上限。**群組不適用**（群組裡的生日祝福常常是祝別人），群組的生日圖維持原本回一張圖。設為空字串 `""` 就關閉，照一般節日圖回覆。最多 20 字。 |
| `text_reply_max_chars` | `30` | 文字訊息超過這麼多字（去掉空白與標點）就當作一般聊天，不回圖。 |
| `auto_open_chat_window` | `true` | 找不到某位對象的獨立聊天視窗時，自動從 LINE 主視窗搜尋並雙擊開啟（名稱必須完全相符；**一律先切到「全部」分頁再搜尋**（必要時暫時拉寬主視窗），做完把你原本的分頁切回去）。設 `false` 就維持手動開視窗。 |
| `auto_bind_by_viewing` | `true` | 未綁定的好友或群組傳來新圖、現有的自動綁定又認不出是誰時，機器人自己**開他的聊天視窗、點開視窗裡一張照片**，看快取有哪一個頻道跟著寫入，確認就是他的頻道才綁定，開出來的視窗做完放回去（一對一與群組都適用，等於自動執行 `--bind-view`）。每位對象失敗後 10 分鐘內不重試，一次最多試 3 位。**會短暫搶走焦點與滑鼠**；不想被打擾就設 `false`，改回手動 `--bind-view`。規則與限制見 v2.15.0。 |
| `log_to_file` | `true` | 程式自己把紀錄寫到 `logs/auto_reply_日期.log`（每天一個檔，內容與畫面相同，包含啟動橫幅與 `[通知]` 提示；**不含聊天內容**），不論用哪種方式啟動都會寫，關掉視窗也留得住。設為 `false` 就完全不寫檔。 |
| `log_keep_days` | `7` | 紀錄檔保留幾天（含今天），更早的自動刪除；只會刪檔名符合 `auto_reply_YYYY-MM-DD.log` 的檔。 |
| `notify_log` | `false` | 把啟動、回覆、停止與警告/錯誤推播到 LINE 官方帳號（例如 `Notify Bot`），在聊天室裡看程式的狀況。需要先建立憑證檔，見下方「Notify Bot 推播」。修改後即時生效。 |
| `notify_monthly_cap` | `150` | 每月最多推播則數。官方帳號免費方案每月上限 200 則（整個帳號共用），預設留 50 則給手動測試。達到上限後改走 `notify_fallback_chat` 備援（見下方），下個月恢復。 |
| `notify_fallback_chat` | `"Notify Bot"` | **推播額度用完時的備援**：LINE 回 429（額度用完）或本月推播數到 `notify_monthly_cap` 時，改從**你自己的帳號**把通知打進這個聊天室（視窗沒開會自動開出來並留著；`auto_open_chat_window` 關閉或開不起來才只寫紀錄檔）。空字串 = 不備援。不能是 `group_targets` 裡的群組。 |
| `max_replies_per_day` | `3` | 每個聊天室每天最多回覆幾次。以本機日期計算（午夜 00:00 重置），記在 `reply_counts.json`，重啟程式不歸零。只計實際送出的回覆；因為不是長輩圖、辨識不出來、競選圖而略過的不算。`0` 表示不限次數。 |
| `max_image_pool` | `120` | 圖庫上限張數：即時抓圖時辨識得出性質但用不到的圖，超過這個數量就不留。 |
| `instant_crawl_max_downloads` | `40` | 圖庫沒有合適的圖時，立即上網抓圖最多下載幾張（節日圖加倍）。 |
| `time_aware_images` | `true` | 對方傳時段問候（早安、午安、晚安）時，依**現在的時段**（05-11 早安、11-17 午安、17-05 晚安）回對應的問候圖；沒有就立即上網抓，還是沒有才改用無時段關聯的圖（祝福、叮嚀、心靈雞湯）。設為 `false` 則不管時段，任何問候圖都可以。節日圖不受影響。 |

## 🧭 一對一聊天室與群組：貼圖與長輩圖的處理差異

群組裡誰都能傳圖、也分不出是誰傳的，所以群組的規則比一對一**更保守**。下面先看「對方傳什麼，機器人會怎麼做」，再看各個環節的差異。

### 對方傳什麼 → 機器人怎麼做

| 對方傳來的 | 一對一聊天室（`targets`） | 群組（`group_targets`） |
|---|---|---|
| **長輩圖照片**（OCR 讀得出節日、問候、祝福等性質） | 回**同性質但不同張**的圖。若是生日祝賀，只回一句「謝謝」（`birthday_reply`） | 回同性質但不同張的圖；生日祝賀的圖**仍回圖**（群組裡的生日祝福常常是祝別人，回「謝謝」可能回錯人） |
| **生活照、寵物照、辨識不出性質的圖** | 略過，記 `[非長輩圖略過]` | 略過（同左） |
| **競選圖**（候選人、競選相關字樣） | 略過，記 `[競選圖略過]` | 略過（同左） |
| **貼圖，上面寫著短問候或祝福**（例如「早安安」） | **回同性質但不同張的圖**（`reply_to_sticker_text`，v2.14.0 起；該好友視窗要展開放背景）；貼圖上是生日祝賀只回「謝謝」 | **略過**（群組的貼圖一律不回） |
| **貼圖，沒有字或字不是問候**（例如「OK啦」「哈哈哈」、純圖案） | 略過，記 `[非長輩圖略過]` | 略過 |
| **短文字問候**（早安、中秋節快樂） | 回同性質的圖（`reply_to_text`）；「生日快樂」只回「謝謝」 | **不處理**（群組不讀文字訊息） |
| `require_grandma_image` 設成 `false` 時的任何照片或貼圖 | 不辨識，照現在時段回一張問候圖 | **設定無效**，群組一律強制辨識，規則同上 |

### 各個環節的差異

| 環節 | 一對一 | 群組 | 為什麼 |
|---|---|---|---|
| 名單 | `targets` | `group_targets`（也會併進監控名單） | 群組另列，不動一對一的嚴格規則 |
| 怎麼偵測有新訊息 | **照片**：LINE 快取目錄出現新檔。**貼圖與文字**：LINE 不把貼圖寫進聊天室的快取（貼圖存在 `Data\Sticker`，依貼圖編號存，與聊天室無關），所以靠「視窗展開、放在背景、訊息列表有變化」偵測 | **只偵測照片**，且只靠已綁定的快取頻道（貼圖與文字都不處理） | 群組標題的數字是**成員數**，不是未讀數，不能拿來觸發；群組也不看視窗列表 |
| 視窗要求 | 想回**文字或貼圖**的好友，視窗要**展開、放在背景**，不能縮小（縮小後 LINE 不顯示任何新訊息記號）；只回照片的好友視窗可以縮小。停止指令聊天室（如 Notify Bot）不看 | 視窗可以縮小，偵測不靠視窗 | 見 v2.12.0 |
| 快取頻道綁定 | 自動綁定（桌面上只開著他一位的視窗，等他傳一張**照片**），或手動 `--bind-view` | **只能手動綁定**：`python auto_reply.py --bind-view "群組名稱"`，30 秒內在該群組視窗點開一張**真正的照片** | 群組裡誰都能傳圖，自動綁定的「一對一核驗」無法確定頻道歸屬，所以自動綁定一律排除群組 |
| 照片或貼圖怎麼分 | 看圖片正下方有沒有「儲存｜另存新檔｜分享」那一列連結：照片有，貼圖沒有。縮圖還在載入時最多等 8 秒 | 同左 | 兩者共用；不看縮圖寬度，也不看快取檔大小（都不準） |
| 長輩圖辨識 | `require_grandma_image`（預設開）可以關 | **強制辨識** | 群組不能亂回 |
| 每天最多回幾次 | `max_replies_per_day`（預設 3） | `group_max_replies_per_day`（預設 **1**） | 多人連續傳圖時不洗版 |
| 兩次回覆的最短間隔 | `cooldown_seconds`（預設 30 秒） | `group_cooldown_seconds`（預設 **600 秒**） | 同上 |
| 誰傳的 | 知道 | **分不出**（記在群組名稱底下） | 群組的百輪「不回傳對方傳過的圖」記憶，以群組當一位對象 |
| 前景視窗標題核對 | 標題帶括號數字就判定是群組，**拒絕發送** | 允許「名稱」或「名稱 (成員數)」，但名稱要符合 | 一對一視窗置前景後未讀數會清掉，不該帶括號 |
| 找不到視窗時自動開 | 搜尋結果**不接受**「名稱 (人數)」那一列（那是同名的群組） | **接受**「名稱 (成員數)」，長名稱被截斷也能對上 | 避免一對一誤開到同名群組 |
| 文字與生日「謝謝」 | 有（`reply_to_text`、`birthday_reply`） | 沒有 | 群組不讀文字，生日祝福可能是祝別人 |

### 貼圖上的字怎麼讀（一對一）
1. **偵測**：貼圖不會寫進聊天室的快取，所以和文字訊息走同一條路：好友的視窗**展開、放在背景**時，機器人監看訊息列表，列表一有變化（有新訊息）就把視窗帶到前景看一眼最底部那一則（`_peek_incoming_text`）。
2. **判斷是不是貼圖**（`_bottom_sticker`）：最底部不是文字氣泡，而且圖片正下方**沒有**「儲存｜另存新檔｜分享」那一列連結（照片有那一列，照片仍交給快取路徑處理）。結果分三種：是貼圖（附裁切圖）、不是、**暫時判斷不出**（截不到圖、判斷不出、例外，例外會留一行 `[貼圖偵測]` 紀錄）。判斷不出時回「稍後重試」，**不會當成不是貼圖而永久略過**。照片還在載入時（灰色小方塊）也沒有那一列，所以「看一眼」判斷時會**每秒重看、最多等 4 秒**（`STICKER_LOAD_WAIT_SECONDS`）：那一列出現就是照片，交給快取路徑；只有真的貼圖（永遠不會出現那一列）會等滿 4 秒。
3. **OCR**（`recognize_incoming_sticker`）：等畫面穩定後取得貼圖的裁切圖，**就用這一張讀**，不會中途改讀文字氣泡；最底部已經不是貼圖就回「稍後再說」。讀字時**先讀原圖**（實測原圖最準，多種前處理反而更差）；讀不出問候時，只有「讀到短字」（可能是小字）才放大 2 倍再讀一次，已經太長的字就不再讀。**一個字都沒讀到**時貼圖可能還在載入，會等 1.5 秒重新截圖偵測再讀一次（只再讀一次），第一輪不放大、放大留給第二輪，所以沒字的貼圖最多讀 3 次 OCR。一般文字訊息不會多付貼圖偵測的畫面穩定等待（看一眼已經等過，文字辨識不再等第二次）。裁切圖會連旁邊的時間（「上午 6:20」）一起框進來，讀得出的時間會被清掉，讀歪的殘渣不含問候關鍵字，不影響分類。文字訊息與貼圖共用同一個讀字函式 `_read_greeting`。
4. **分類**：讀到的字套用和**文字訊息完全相同**的規則（`classify_message`）：`text_reply_max_chars`（預設 30）字內、競選字不算、生日要有祝賀語（「生日快樂」之類）才算。分類得出節日、時段問候、平安叮嚀、祝福鼓勵、心靈雞湯才回，其餘（沒字、「OK啦」「哈哈哈」）一律略過，記 `[貼圖略過]`。
5. **之後的流程與文字訊息相同**：先看一眼（不是問候就不用等）、隨機等待、等完再確認一次、挑同性質但不同張的圖、生日祝賀只回「謝謝」、送達確認、每日上限與冷卻。
6. **文字與貼圖各有各的開關**：`reply_to_text` 管文字，`reply_to_sticker_text` 管貼圖。只開貼圖、關掉文字時，文字問候在「看一眼」通過之後**立刻略過**（不會先隨機等待最多 900 秒才略過，那會卡住其他好友），生日祝賀仍照 `birthday_reply` 回「謝謝」。
7. OCR 暫時不能用時回傳「稍後再辨識」，不會當成不是問候。

**已知限制與風險**：
- **視窗不能縮小**，停止指令聊天室不適用；你正在看那個視窗（它是前景而且沒被蓋住）時只更新記錄、不觸發。
- 機器人只看聊天室**最底部**那一則，貼圖之後如果又有別人的訊息把它推上去，就看不到了。
- OCR 對裝飾字型、動態貼圖、很小的字可能讀不準，**讀不準的後果只是不回，不會亂回**（分類看關鍵字）。
- **照片被當成貼圖的機率**：照片的「另存新檔」那一列要等圖載入完成才會出現，所以「看一眼」判斷時會等最多 4 秒；網路特別慢、4 秒內還沒載入完成的照片仍可能被當成貼圖讀字（讀到問候才會回，之後快取路徑看到同一張照片可能再回一次）。
- **量測結果**：真實的「早安安」貼圖（取自理財幼幼班，只做唯讀截圖與 OCR）5 種 OCR 做法全部讀對；用字型畫出的貼圖風格問候字 64 張讀對 63 張；LINE 官方 8 張角色貼圖與 40 張非問候字零誤判。

## 🛠 開發流程：commit 前的審查關卡（Claude Code hook）

用 Claude Code 開發這個專案時，`git commit` 之前一定要先跑過三個審查：`/simplify`（整理重複與可簡化之處）、`/code-review`（找 bug 與邏輯問題）、`/security-review`（找安全問題）。hook 只能執行 shell 指令、沒辦法直接呼叫 slash 技能，所以做成「關卡」：

| hook | 時機 | 做什麼 |
|---|---|---|
| `record` | `PostToolUse`，工具是 `Skill` | Claude 每執行一次上面三個技能就記一筆 |
| `gate` | `PreToolUse`，工具是 `Bash`（只對 `git ...` 指令） | 偵測到 `git commit`，三個審查沒跑齊就**擋下**，訊息會列出缺哪幾個、要怎麼補 |
| `clear` | `PostToolUse`，工具是 `Bash`（只對 `git ...` 指令） | `git commit` 成功後清空紀錄，下一輪重新計 |

- 設定在 `.claude/settings.json`（進版控），程式在 `.claude/hooks/review_gate.py`，紀錄在 `.claude/review-state.json`（不進版控）。
- 你自己在對話框手動打 `/code-review` 時，不會經過 Claude 的 `Skill` 工具，紀錄不到：用 `python .claude/hooks/review_gate.py mark code-review`（或 `simplify`、`security-review`）補記錄；`python .claude/hooks/review_gate.py status` 可以看目前記了哪些。
- 判斷 `git commit` 時會先拿掉引號與 heredoc 裡的字，所以 commit 訊息裡提到「git commit」不會被誤擋；`git status`、`git push`、`git commit-tree` 等也都不會被擋。
- **關卡壞掉會放行**（只在 stderr 留一行），不會讓你什麼都 commit 不了。
- 限制：記的是「執行過」，不是「審查結果都處理完了」；審查是背景執行的，要等它回報、處理完再 commit 是紀律，不是 hook 能檢查的。

### 紀錄檔與推播的分工
- **紀錄檔**（`log_to_file`，預設開）：程式自己寫 `logs/auto_reply_日期.log`，每天一個檔、保留 `log_keep_days` 天，`logs/` 不進版控。這是完整的運作紀錄，掛掉或漏回時回頭查原因用。
- **Notify Bot 推播**（`notify_log`，預設關）：只推啟動、回覆、停止與警告，要有 `~/.line-notify.env` 的權杖。
- **另一台電腦的 LINE 沒有 Notify Bot 聊天室**：`notify_log` 維持 `false`（預設）即可，紀錄只出現在畫面與 `logs/` 檔案，完全不連網推播。就算開著：找不到憑證只會印一行提示；推播被 LINE 拒絕（HTTP 400/401/403/404，例如那個帳號沒加 Notify Bot 為好友）時，本次執行**自動不再推播**，紀錄照樣寫在檔案裡；把 `notify_log` 關掉再打開、或重新啟動，會再試一次。

### 推播額度用完時的備援（`notify_fallback_chat`）
- **什麼時候啟動**：LINE 回 429，或本月推播數到 `notify_monthly_cap`。之後的通知不再丟掉，先暫存（最多 200 則）。
- **怎麼送**：主迴圈有空時，最多每 5 分鐘一次，把累積的通知合併成一則（開頭標「📝[備援]」，換行改成「／」，每則之間用「｜」），把視窗帶到前景、用你的帳號打進輸入框送出，再放回去。視窗沒開時照 `auto_open_chat_window` 自動從主視窗搜尋開出來（v2.15.0 起；開出來的**不會**登記成「用完要關」，會一直留著並最小化，因為停止指令偵測也要這個視窗存在）；`auto_open_chat_window` 關閉或開不起來就不送（找視窗每 30 秒一次，開窗失敗最短隔 5 分鐘才再試；程式結束前的最後一次不開窗），通知仍完整寫在 `logs/` 檔案。
- **不會把自己停掉**：停止指令是「你自己發的訊息裡含那句話就停」，備援訊息正是從你的帳號送出。所以備援內容裡的停止指令字樣一律換成「（停止指令）」，換完還會逐則與整段各檢查一次，仍然像停止指令的整則省略。
- **不會誤用**：帳號沒加 Notify Bot 為好友（400/401/403/404）或找不到憑證時，維持只寫檔案，不往聊天室塞東西；輸入框裡有尚未送出的草稿、焦點被別的視窗搶走時不送，保留通知，下一個間隔再試。
- **送不進去時**：間隔拉長到 15 分鐘再試，並改送去掉表情符號與符號的版本（輸入框可能改寫它們，造成讀回比對失敗）；視窗沒開時每 30 秒才找一次。
- **程式結束前**（Ctrl+C、遠端停止指令）會再送最後一次，額度用完時「已停止」是最想看到的通知（視窗有開才送）。
- **代價**：送出時 Notify Bot 視窗會短暫跳到前景，你正在打的字可能被打斷，所以才合併、並限制最多 5 分鐘一次。

### Notify Bot 推播

把程式的重要事件推到你的 LINE，不用一直看電腦。需要一個 LINE 官方帳號（Messaging API），並先加為好友：

1. 在 `~/.line-notify.env`（可用環境變數 `LINE_NOTIFY_ENV` 指定路徑；找不到時改讀 `~/.line-test.env`）寫入：
   ```
   LINE_TOKEN=<Channel access token (long-lived)>
   LINE_USER_ID=<你的 User ID，U 開頭>
   ```
2. `config.json` 設 `"notify_log": true`。
3. 推播的內容：
   - 🟢 啟動（版本、監控名單、停止指令聊天室）
   - 📨 每次回覆長輩圖（對象與檔名）
   - 🔴 停止（Ctrl+C 或停止指令）
   - ⚠️ 警告與錯誤：`[安全隔離]`、`[警告]`、`[錯誤]`、`[例外防護]` 開頭的 log，以及 logging 的 WARNING 以上。同一類 30 分鐘最多推一次，全部每小時最多 6 則。完整 log 仍在本機。
4. 額度保護：本機用 `notify_state.json` 記本月用量，每次啟動後第一次推播會向 LINE 查實際用量（手動測試用掉的也算），達到 `notify_monthly_cap` 就不再推；LINE 回 429 也視為本月用完。推播在背景執行，網路慢或失敗不會影響監聽，只在本機印出「[通知]」提示。

**注意**：如果推播的聊天室同時在 `targets` 裡，且 `trigger_mode` 為 `all`，推來的文字會被當成對方訊息而觸發回覆；請用預設的 `photo_and_sticker`。

#### 未綁定的好友與群組：偵測到新圖時，自動開窗、點圖、綁定，綁完把視窗放回去
- **起因**：紀錄裡反覆出現「偵測到 2 個不同之未知快取頻道，拒絕自動綁定」。原本的自動綁定要「桌面上只開著他一位」、而且群組一律只能手動 `--bind-view`，所以 `targets` 裡新加的好友與群組很難綁上。
- **做法**（`view_binder.py`，設定 `auto_bind_by_viewing`，預設開）：未綁定的快取頻道有新圖、現有自動綁定又沒綁成時，依序替「還沒綁定的對象」做這幾步：開他的聊天視窗（沒開才開，沿用 `auto_open_chat_window`）→ 帶到前景 → 點開視窗裡看得到的一張照片 → 觀察約 6 秒，看快取有哪一個頻道寫入 → 確認後綁定 → 按 Esc 關掉放大檢視 → 開出來的視窗放回去（本來就開著的不動）。
- **核驗（Fail-Closed，沿用 `--bind-view`）**：點圖前聊天視窗必須在前景、標題剛好是這個對象（群組可帶成員數）、點的位置必須落在這個視窗上；觀察期間快取有寫入的頻道**必須剛好 1 個**，而且每次寫入當下前景標題都還是這個對象。找不到照片、點了沒寫入（最多換 3 張）、點完前景不對、被別的視窗蓋住，一律不綁。
- **不會把自己點圖當成對方傳新圖**：點圖造成的快取寫入（含結束後 3 秒內）一律標成已處理，不會觸發回覆。代價：這段期間真的有人傳來的圖也會被略過。
- **節奏**：每位對象失敗後 10 分鐘內不重試；一次觸發最多試 3 位，視窗已經開著的優先。綁成功就停。觸發當下的那張圖不回，下一張起生效。
- **找照片靠截圖，找不到會往上捲**：目前版本的 LINE 不再把訊息內容暴露給 UIA（每則訊息底下都沒有子控制項），所以改用截圖找：大的、不是純色氣泡（灰色對方氣泡、綠色自己的氣泡）的區塊才算照片，對方傳的優先，不夠才找自己傳的。視窗裡看不到就用滾輪往上捲最多 5 頁，做完捲回原位。照片比歷史區還高（常見）時，露出的部分夠大就點露出部分。
- **點圖前先等快取安靜**：自動綁定正是在「某個頻道剛有新圖」時觸發，那個頻道可能還在寫檔；不先等它寫完，它的寫入會被誤當成點圖造成的，綁到錯的人。所以點圖前要連續兩次快取快照相同，一直在變就不點、不綁。
- **失敗後指數退避**：同一位對象失敗後等 10 分鐘，連續失敗每次加倍，最多 6 小時，成功就歸零（非監控對象一直傳圖時，不會一直去搶你的滑鼠）。
- **開窗比對容許名稱最後一個字被 OCR 吃掉**（`chat_opener.py`）：真機上「李月琴@全球人壽」被讀成「李月琴@全球人」，沒有刪節號，整列比對失敗。現在最多容許少一個字、前綴至少 5 字、後面只能接成員數與時間、整個搜尋結果裡剛好一列（與截斷的列合併計算）；雙擊後仍要等到標題完全相符的視窗才算成功。

- **尚未驗證的**：**還沒有對「未綁定的好友」真的完成一次綁定**（只驗證了偵測到的頻道正確）；Esc 是否確實關掉放大檢視只看到測完前景仍是聊天室；點到貼圖會怎樣沒測。
- **開窗比對的最後一招：信任 LINE 自己的搜尋**：名稱很長或字體讓 OCR 把中間的字吃掉、讀成別的字時（真機：「翁彦臻(公羽)凱基人壽/信託咨詢」被讀成「翁彦臻(公羽)凱基人/..」，「壽」讀成「嘉」或不見），前面的完整、截斷、少一字三種比對都對不上。現在這三種都找不到時，改看搜尋結果的小標題：「聊天」小標題的筆數剛好是 1（LINE 認定恰好一個聊天室的名稱符合我們打進去的整串名稱）才雙擊它底下第一行最左邊的字框（不是同一行右邊的時間，也不是下一行的預覽），而且那段文字要跟名稱有一定相似度。沒有「聊天」小標題（沒有聊天記錄的人，例如很久沒聊天、LINE 電腦版沒保留）、筆數不是 1、有兩列以上截斷符合的，一律不點；雙擊後仍要等到標題完全相符的視窗才算成功。**簡繁互轉不是這個問題的原因**（真機 OCR 資料顯示 OCR 讀歪的是字本身，轉換表救不了）。真機驗證（2026-11-07）：翁彦臻自動開窗成功。**沒有聊天記錄的人**（例如陳惠萱，搜尋只有「訊息」區塊）自動開窗開不起來，等她傳訊息、聊天出現在清單後就找得到。

- **機器人自己開的視窗，用完直接關掉**（`close_opened_windows`，預設開）：自動開窗時，只有「開窗前桌面上沒有、開窗後才出現」的視窗會登記（記下 hwnd 與對象名稱），所以你本來就開著的視窗不會被登記。在送出流程**真的結束**時用 `WM_CLOSE` 關閉：送出成功、確定略過（不是問候、沒有合適圖片、達每日上限等）、自動綁定結束；要重試的路徑（`NOT_SENT`）與「看一眼」那一步不關，免得重試時得重新開窗，之後真正結束時才關。**關閉前再核對**：視窗標題仍是登記的對象（hwnd 被別的視窗重用就不動）、不是文字偵測正在監看的視窗（關掉會偵測不到下一則）、登記不到 1 小時；送出關閉後確認視窗真的消失才算數，LINE 沒理就改成最小化並保留登記。真機驗證（2026-11-07）：只關掉那一個聊天視窗，LINE 主視窗與其他聊天視窗不受影響；標題對不上的登記不會關。
- **讀最底部那一則之前，先把視窗捲到最下面（只對你沒在看的視窗）**：視窗若停在你捲過的舊位置，機器人讀到的會是舊訊息。現在回覆流程（含「看一眼」判斷是不是短問候的那一步）在把視窗帶到前景、讀字之前，會先判斷你有沒有正在看它：**在看就完全不動**；沒在看才把滑鼠移到訊息列表、滾輪一輪一輪往下捲，每輪等畫面穩定，捲了畫面也不再變就是到底了（最多 12 輪，已經在底部約 2 輪）。「你有沒有在看」必須在機器人把視窗帶到前景**之前**量，否則一帶到前景就永遠算你在看。判斷不出來時保守當成你在看，不捲。停止指令的偵測不在這次範圍。真機驗證（2026-11-07）：往上捲 6 輪後畫面明顯不同；你在看時畫面完全沒變；你沒在看時捲回去，與最底部畫面一致。

- **修正：照片被當成貼圖、貼圖被當成照片**（真機：理財幼幼班_Z 傳來早安照片，紀錄卻是「不是照片 (疑似貼圖)」而沒有回）。原因有兩個：
  - v2.9.0 的群組用「快取檔 ≥ 250KB 才是照片」判斷，但 LINE 的照片快取多半很小（Notify Bot 的 38 張照片裡 33 張小於 250KB，中位數 112KB；那張早安圖只有 13KB）。**群組不再用檔案大小判斷**，所有新圖都交給視窗截圖辨識。

  - 群組**一律強制辨識**，即使 `require_grandma_image` 設為 `false` 也一樣。
- 已知取捨：群組的貼圖也會讓視窗被還原到前景一下才判斷得出來（當天還沒回覆過、尚未達每日上限之前）；達到每日上限後在開視窗之前就直接略過。

### [v2.7.0] - 2026-10-31
#### 依對方傳來的圖，回同性質但不同張的圖
- **OCR 換成 RapidOCR（離線）**：Windows 內建 OCR 對藝術字很不準（30 張隨機圖只讀得到 2 張的問候語），RapidOCR 讀得到 15 張，而且沒讀到問候語的圖文字也讀得準。每張約 0.5 秒。需要 `pip install rapidocr-onnxruntime`（已加入 `requirements.txt`，約 270MB，含 onnxruntime 與 opencv）；沒安裝時啟動會明確警告，並退回 Windows OCR（辨識率大幅下降，多數圖會辨識不出來而被捨棄）。

- **每個聊天室每天最多回覆 3 次**（`max_replies_per_day`）：本機午夜重置，只計實際送出的。
- **圖片載入中不下結論**：LINE 載入圖片時先顯示一個灰色小方塊，會被看成文字氣泡或貼圖。現在辨識截圖時內容太小每秒重截一次，最多等 8 秒；被圖片快取觸發時，訊息類型被判成文字也會重試，最多等約 8 秒。
- **啟動時**回報用哪一套 OCR，並在背景預先辨識整個圖庫（結果快取在 `image_kinds.json`），完成後印出各性質的張數。
- **真機驗證**：早安圖 → 晚上回晚安圖；聖誕節圖 → 圖庫沒有同節日的圖，立即上網抓到另一張聖誕節圖並回覆；祝福圖 → 回另一張祝福圖；同一個聊天室第 4 次 → `[每日上限]` 不回覆。
- **已知限制**：縮圖大小下候選人圖的字常常讀不到（12/15 讀不到任何競選字眼），這時是「辨識不出來」而不是「看懂是競選圖」，結果一樣是不回覆；但若縮圖剛好只讀到祝福字眼（例如「幸福」），仍可能被當成祝福圖。

### [v2.3.0] - 2026-10-29
#### 誤傳防護與對象嚴格隔離 (Accidental Send Prevention & Strict Window Isolation)
- **徹底廢止主視窗模擬搜尋鍵盤輸入**：完全移除過去在主視窗點擊搜尋框、模擬複製貼上聯絡人名稱與模擬鍵盤 Enter 尋找對話框之邏輯。徹底杜絕因焦點漂移或停留在其他聊天室輸入框時，誤將好友姓名以文字訊息送出給錯誤對象的災難性風險。
- **微秒級前景視窗標題雙重核驗 (Strict Foreground Whitelist & TOCTOU 防禦)**：發送長輩圖前強制比對 Windows 頂層焦點視窗（Foreground Window）之真實標題。標題若為「LINE」主視窗、群組、或任何非目標好友之名稱，立即觸發 `[致命安全攔截]` 中止發送，絕不在未確認目標身分的視窗執行貼上動作。
- **三態發送送達確認架構 (NOT_SENT / SENT_CONFIRMED / SENT_UNCERTAIN)**：發送前失焦判定為 `NOT_SENT` 並進入最多 3 次安全重試；Enter 送出後由專屬送達核驗函式驗證右側氣泡，明確送達確立為 `SENT_CONFIRMED`；未見氣泡則判定為 `SENT_UNCERTAIN` 並記入發送歷史且絕不自動重試（若頻率超標則啟動斷路器退避），徹底杜絕重複洗版發送長輩圖。
- **重名與重複開啟全量攔截**：合併精確與括號候選視窗並去重 HWND，即便一已讀一未讀，只要桌面存在超過 1 個同名視窗一律攔截拒發。
- **群組名稱關鍵字安全過濾**：為徹底防範將群組誤判為個人對話，名稱若包含「群組、聊天室、成員、專案、公務、同學、家族、group、team、club、project、family」等字樣，程式一律判定為群組並安全攔截（Fail-Closed 拒發）；若目標好友名稱包含上述關鍵字，建議於 LINE 中微調好友備註名稱。
- **零設定全自動頻道學習綁定 (Zero-Config Auto-Discovery & Auto-Binding)**：徹底廢除強制手動校準要求。單一監控對象或多對象視窗上線時，系統自動辨識底層快取頻道並動態完成映射持久化，完全開箱即用；同時原生支援現代電腦版 LINE 獨立視窗標題正常無未讀括號特性，消除等待括號卡死問題。
- **暫定綁定二次核驗 (Fail-Closed)**：自動學習的綁定先為暫定狀態，需經獨立傳入圖片核驗才轉為永久；核驗通過前一律不回覆，因此綁定後 6 秒內的後續圖片不會被回覆。目標視窗閒置且指紋已轉入其他訊息時自動撤銷錯綁。
- **跨版本快取目錄雜湊萃取相容**：同時相容 LINE 電腦版不同版本之單層與雙層 40 字元快取子目錄架構，確保監聽指紋精準鎖定目標對象。

#### 核心安全修復與深層防禦 (Critical Hardening & Architecture Upgrade)
- **多層深層防自循環架構 (Multi-Tier Self-Reply Defense)**：
  - **實體快取三元組差集快照**：發送前後自動對快取檔案進行路徑、修改時間（mtime）與檔案大小（size）全量差集快照，本機發送產生的新檔案或就地更新均自動記入黑名單。
  - **Windows DWM 像素實體位置方向核驗 (Fail-Closed)**：發送前核驗目標聊天室為前景視窗，透過 DWM 精準擴展客戶區邊界與動態 DPI 感知取樣，雙欄模式嚴密隔離側欄；最底部訊息若位於右側或無法判斷時一律安全攔截中止發送。
  - **跨重啟雙重持久化斷路器 (Circuit Breaker)**：同一對象 5 分鐘內最多回覆 2 次，超標啟動 30 分鐘退避鎖定；鎖定期、時間戳與 5 秒發送防抖保護全量持久化至 `circuit_breaker.json`，重啟常駐程式不失效。
  - **未讀視窗交叉驗證之頻道關聯**：底層媒體快取雜湊不盲目自動綁定單一好友，僅在該好友視窗出現實體未讀訊息時才安全關聯，徹底防止群組貼圖誤判。
  - **全方位多語系發送排除**：嚴格排除「您傳送了」、「You sent」、「写真を送信しました」等本機發送通知與文字。
- **全面支援 LINE 貼圖 (Sticker)**：
  - 關鍵字辨識庫擴充納入 `[貼圖]`、`[照片]`、`\b(photo|image|sticker)\b`。
  - 新增 `trigger_mode` 設定值 `"photo_and_sticker"`（同時支援長輩圖照片與 LINE 貼圖觸發）。

- **借花獻佛大循環**：自動辨識並收納好友傳送之正統長輩圖進中央圖庫，日後可流通發送給其他好友（原發送者百輪內封印不回發）。
- **台塑貼圖酷官方爬蟲**：直接介接 Formosa「台塑貼圖酷」長輩圖專案，精選上千張每日問候圖，支援連線熔斷保護與 7 天 TTL 自動過期清理。
- **Windows 原生繁中 OCR**：內建整合 `Windows.Media.Ocr`，自動核對問候關鍵字，自動過濾生活照、發票收據等非長輩圖。
- **動態名單熱更新 (Hot Reload)**：背景常駐期間修改 `config.json` 好友名單秒級生效，無需重啟程式。

#### 健全度與效能最佳化
- **Per-Monitor V2 DPI 感知**：支援高解析度螢幕縮放（125%、150% 等），避免滑鼠座標偏移。
- **檔案原子寫入 (Atomic Write)**：使用暫存檔與 `os.replace` 儲存 JSON，杜絕斷電或非預期中斷造成資料損壞。
- **全域日誌與版本號標記**：所有控制台輸出與日誌均自動附帶時間戳記與版本號標籤 `[v2.2.0]`。
- **命令列工具鏈完善**：提供 `--version`、`--crawl`、`--test`、`--list-images`、`--scan-windows`、`--clear-history` 等豐富除錯與管理參數。

#### 隱私與安全防護
- **個人隱私防護**：將 `config.json`、`contact_history.json`、`chat_dirs.json` 列入 `.gitignore`，徹底杜絕真實好友名單上傳公開儲存庫。
- **說明文件去辨識化**：所有公開說明文件、程式範例與日誌輸出均全面去除真實個人姓名，一律採用「媽媽」、「爸爸」、「大舅舅」等通用尊稱佔位符。

## 🤖 多 AI 交叉審查標準開發規範 (Multi-AI Cross-Review Protocol)

本機環境具備四大頂級 AI 開發工具生態：
* **Antigravity** (Google DeepMind)
* **Claude Code** (Anthropic Claude CLI)
* **OpenAI Codex** (OpenAI Codex CLI)
* **GitHub Copilot** (GitHub Copilot CLI)

### 核心開發準則 (Golden Rule)
> **「凡由任一 AI 開發或修改完成之程式碼，必須第一時間主動送交給本機其他不同的 AI 開發工具進行獨立嚴格交叉審查（Cross-Review），徹底消除單一模型之認知盲點，收斂所有重大架構與安全性疑慮後方得視為交付。」**

#### 審查意見嚴重度分級與反覆修復流程 (Severity & Remediation Protocol)：
1. **意見分級規範**：審查工具（Reviewer）產出的審查意見必須嚴格分為三級：
   - **🔴 高度嚴重意見 (High / P1)**：邏輯無窮迴圈、誤傳至非目標對象、程式崩潰、未釋放資源、或核心安全漏洞。
   - **🟡 中度嚴重意見 (Medium / P2)**：邊界條件不嚴謹、可能遺漏事件、狀態持久化不同步、文件與實作矛盾。
   - **🟢 低度嚴重意見 (Low / P3)**：程式碼風格最佳化、註解潤飾、微小相容性建議、未追蹤檔案整理、非台灣用語等。
2. **高／中度嚴重意見強制循環修復 (Mandatory Re-Review Loop)**：
   - 被審查者（Developer）**必須強制全數修復所有高度（High）與中度（Medium）嚴重意見**。
   - 修復完成後，**必須再次送回原審查 AI 工具進行第二輪審查**。
   - 此送審 → 修復 → 覆審之循環流程**必須持續迭代，直至所有審查 AI 確認「無任何高度與中度嚴重意見」為止**。
3. **低度嚴重意見處置**：
   - 低度嚴重意見（Low / P3）由被審查者人工判斷是否修復。
   - 僅修復低度意見後，**不必再次送審**。

#### 執行標準作業程序：
1. **修補檔匯出**：程式碼撰寫完成並通過單元測試 (`python -m unittest discover -s tests`) 後，匯出最新 `git diff` 修補檔。
2. **三方獨立送審**：非本體的其餘三款 AI 工具各自啟動獨立工作階段進行審查：
   - `claude.cmd -p -` (Claude Code 深度程式碼審查)
   - `copilot.cmd -p ...` (GitHub Copilot 架構安全審查)
   - `codex.cmd exec` (OpenAI Codex 推理審查)
3. **台灣用語審查（每輪必含）**：審查報告必須獨立列出「台灣用語」一節，逐一檢查 README、程式註解、日誌訊息與測試說明，凡出現中國大陸慣用語（例如：進程、代碼、調用、運行、打開、優化、設置、窗口、激活、函數、閉環、死循環）一律列為低度意見，並提供台灣用語替換（行程、程式碼、呼叫、執行、開啟、最佳化、設定、視窗、啟用、函式、反覆修復、無窮迴圈）；若無則須明確寫「台灣用語：無問題」。
4. **版次號碼規則（語意化版本 主.次.修）**：
   - 主版：不相容改動（例如設定檔格式或指令改名，使舊設定失效）。
   - 次版：新增向下相容的功能。
   - 修訂：只修錯誤，不新增功能。
   每次改版須同步更新 `auto_reply.py`、`crawl_images.py` 的 `VERSION`、`run_auto_reply.bat` 標題、README 徽章、檔案結構中標有版次的註解與更新紀錄，並隨該次改版一併送審。
5. **報告存檔與反覆迭代**：各工具輸出之獨立審查報告存檔至本機，確認達成「零高、中度嚴重意見」之驗證標準。
